The Poetry of Plainness

The honest tool names what it is, and stripping the metaphor back to plainness is an act of respect

  • naming
  • software-design
  • developer-tools
  • simplicity
  • refactoring

There is a particular agony in finding out what you built. The metaphors you chose at the start develop their own gravity, pulling inward until nobody can remember why a project tracker was supposed to be an operating system, or what it meant for a task manager to have a brain, or why persistent state was called a pointer when what was meant was where you left off.

This is the story of digging down to what the names were covering.

Somewhere in a developer tools project, someone decided that the core organizational structure should borrow its vocabulary wholesale from operating systems. There would be an os. There would be state living in nested directories. There would be epics grouping goals like narrative containers, and it all felt like a whole system with the rhetorical weight of something serious, so you could talk about processes and state management and sound like you knew what you were doing. The metaphors were chosen the way people choose furniture, because they made the empty room look furnished. An operating system runs hardware; a tool tracks goals, and the distance between those two jobs is where the sediment started to form.

Extended metaphors are sticky, they calcify, and the agents using the tool were receiving instructions about a project brain and a user machine os, until everyone paused to think that the project had become a Babel. The refactoring was not born from a grand design impulse; it came from the recognition that the naming had become a liability, obscuring rather than clarifying what was actually happening — a folder structure, some files, and a place that keeps track of what you are working on right now. The deeper question was not whether the system worked, but whether it was intelligible.

The Great Un-epicking

The first move was brutal and clean: delete the epics. No migration path, no backward-compatibility grace period, just gone. An epic was a container inside the container, goals inside epics and tasks inside goals, and somewhere in that nesting the original intent got lost. Goals and tasks were sufficient, and epics were the turkey having a turkey stuffed inside it.

Removing something placed deliberately requires a confidence that only comes from asking what the thing is actually doing, who it serves, and what breaks if it goes. When the answer is nothing really breaks, and it was mostly conceptual overhead, you have to live with the decision and everything downstream of it.

The templates changed, the documentation shifted, and every bundled skill had to be regenerated.

Then came the small elegance. Runtime state moved from a nested directory of pointer files to a single file at the root of the config, and instead of a directory architecture for what is, in truth, just which task the user is currently working on, there is a file, twenty-two bytes, one fact. It says: no conceptual model is needed for this, only a fact, and a fact can live in one place, be easy to find, and require no hunting. The state file does not explain itself, which is exactly why it does not need to.

The Sweep

The syntax error came next, and it was instructive in its way. A line of frontmatter in a skill template began with a backtick, and YAML rejected it, because a plain scalar cannot start with a backtick, and the fix was a pair of quotes around the whole sentence.

It is the moment the tooling asserts itself, the machine saying it has rules and you must follow them. This is the quiet kind of friction, not the dramatic kind — an extra set of quotes, a reformatting of a thought, a moment of translation between what you meant and what the format will accept. The fix worked, and the question that followed was the useful one: if one line violated the rules, might there be others.

So came the sweep, a script that parsed every piece of frontmatter across all the templates, hunting for violations, and the result was reassuring in its way: there was only the one, a single line in a single file, and the exercise itself was a form of care, a statement that the system does not want friction and is willing to do the work of checking. A format with rules is not an enemy; it is the ground you build on.

The Bedrock

None of this was needed for the tool to work. It was working before; the metaphors were doing their job, the nested state was tracking state, the epics were grouping things. But none of it was as clear as it could be, and in developer tools clarity is everything, because the people using them are builders with high standards. They can smell condescension, and they notice when a tool requires them to think in ways that do not match how they think.

So the refactoring is, in the end, about respect. The refactored tool says to its user: I am not going to make you translate, and I am not going to make you carry metaphors around. The machine is just user-level config; the project memory is just a folder with files in it; the state is a small file that remembers what you were doing.

Plainness is the deepest layer, and you do not dig past it.

Strip away everything that does not serve clarity and watch what remains. Usually what remains is simpler and better than what you started with, and it is the same system, now honest about what it is. A folder is a folder, a file is a file, and the tool tells you where you left off without asking you to believe in a brain.

Naming is the design.
