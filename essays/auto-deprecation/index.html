Auto-Deprecation: Decay Classes & Staleness Detection

How Seme detects and archives stale facts using configurable decay thresholds

1. The Problem of Stale Facts

Memory systems accumulate facts over time. "The user lives in London" was true when stated, but the user moved to Edinburgh six months ago. The system still has the London fact as "active" because the user never explicitly corrected it. Stale facts pollute retrieval and cause the LLM to give outdated answers.

Auto-deprecation is the process of detecting facts that haven't been reinforced in a configurable time window and marking them as archived (not deleted — archived for audit trail). This keeps the active memory store clean while preserving history.

2. Decay Classes

Not all facts decay at the same rate. Seme assigns each memory a decay class:

Decay ClassThreshold (days)Example
exempt365Name, identity core facts
slow90Home city, dietary restrictions
medium30Preferences, interests
fast7Transient states, current mood
session1Session-specific context

The threshold is the number of days since the memory was last reinforced (or observed, if never reinforced) before it becomes eligible for deprecation.

3. Staleness Detection Algorithm

The auto-deprecation process runs as follows:

  1. Query all active memories from SQLite
  2. For each memory, compute daysSince = now - last_reinforced_at (or observed_at)
  3. Look up the threshold for the memory's decay class
  4. If daysSince > threshold, mark the memory as archived with a deprecation reason
  5. Log the deprecation in the healing_log for audit
for (const memory of activeMemories) {
  const threshold = thresholds[memory.decay_class] || 30;
  const lastDate = new Date(memory.last_reinforced_at || memory.observed_at);
  const daysSince = (now - lastDate) / (1000 * 60 * 60 * 24);
  if (daysSince > threshold) {
    archive(memory, `Not reinforced in ${daysSince} days`);
  }
}

4. Reinforcement Tracking

Memories are "reinforced" when:

  • The user mentions the fact again (reinforcement_count++)
  • The user gives positive feedback (compliment_specific, re_engagement)
  • The sleep job finds corroborating evidence

Each reinforcement updates last_reinforced_at, extending the memory's active lifetime. A fact that's mentioned weekly will never be deprecated.

5. Configurable Thresholds

Thresholds are configurable per decay class via the API:

GET /deprecation/thresholds
→ { "session": 1, "fast": 7, "medium": 30, "slow": 90, "exempt": 365 }

POST /deprecation/run
→ { "deprecated": [...], "total_deprecated": 5 }

This allows tuning the system for different use cases. A high-frequency conversation app might use shorter thresholds; a long-term knowledge base might use longer ones.

6. Integration with Sleep Job

Auto-deprecation runs as part of the sleep/consolidation job, alongside memory dedup, entity dedup, and contradiction detection. The sleep job is triggered manually, on idle, or on session count thresholds.

7. Design Decisions

  • Archive, not delete: Deprecated memories are marked as "archived", not removed. This preserves audit history and allows "undo" if the deprecation was wrong.
  • Per-decay-class thresholds: Different facts have different lifespans. A user's name should last forever; a "I'm tired today" fact should decay in hours.
  • Reinforcement extends life: A fact that's repeatedly mentioned or confirmed never decays. This naturally keeps important facts active.
  • No hard deletion: Even after deprecation, the memory exists in the database. The profile compiler excludes archived memories, but they can be restored.

Trade-off: Auto-deprecation uses a simple time-based threshold. It doesn't consider whether the fact is still relevant (e.g., "I live in London" might be stale even if recently reinforced, if the user moved). A more sophisticated approach would use semantic contradiction detection, but that requires an LLM call per memory, which is expensive.
