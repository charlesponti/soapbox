Temporal Queries: Bi-Temporal Memory & As-Of Snapshots

How Seme supports time-based filtering and historical reconstruction

1. The Need for Temporal Awareness

Memory systems accumulate knowledge over time. "The user lives in London" was true in January, but "The user lives in Edinburgh" is true in October. A naive system either overwrites the old fact (losing history) or keeps both (causing contradictions). Temporal queries let you ask: "What did we know at time X?"

This is the foundation of bi-temporal data modeling: tracking both when a fact was true in the real world (valid time) and when the system learned it (transaction time).

2. Temporal Parameters

Seme supports three temporal parameters on retrieval and search:

  • since: Only return memories observed after this timestamp. "What have we learned since March?"
  • before: Only return memories observed before this timestamp. "What did we know before the move?"
  • asOf: Return memories as they existed at this point in time. "What did we know on October 1st?"

These are normalized internally: since → from, before/asOf → to, with asOf also setting historical: true.

3. SQL-Level Filtering

Temporal filtering is applied at the SQL level, not in application code:

SELECT * FROM memories
WHERE status = 'active'
  AND observed_at >= ?  -- since
  AND observed_at <= ?  -- before/asOf

This is efficient because observed_at is part of the memory record. No additional joins or subqueries needed.

4. As-Of Snapshots

An "as of" query returns the state of knowledge at a specific point in time. This is implemented by filtering memories where observed_at <= asOf_timestamp. Combined with the supersession chain (superseded_by_id, supersedes_id), this enables reconstructing the knowledge state at any historical point.

For example: "What did we know about the user's home city on October 1st?" returns "London" if the Edinburgh fact was observed on October 15th.

5. Bi-Temporal Model

Seme's memory records have two timestamps:

  • observed_at: When the fact was true in the real world (valid time). "I moved to Edinburgh on October 1st."
  • recorded_at: When the system learned the fact (transaction time). "The system recorded this on October 2nd."

Currently, both are set to the current time during extraction. A future enhancement could distinguish them: the user says "I moved last week" → observed_at = 7 days ago, recorded_at = now.

6. Integration with Hybrid Search

Temporal parameters are passed through to the hybrid search, which filters memories at the SQL level. The turns, wiki, and graph layers are not temporally filtered (they don't have timestamps on individual records), but the memory layer is.

This means a temporal search returns: memories from the time range + all wiki pages + all graph entities + all matching turns. The temporal filter narrows the memory layer only.

7. Design Decisions

  • SQL-level filtering: Temporal filters are applied in SQL, not application code. This is faster and ensures consistent results.
  • Observed_at as the filter key: Uses observed_at (when the fact was true) rather than recorded_at (when the system learned it). This matches user intent: "What did we know in March?" means "what facts were true in March."
  • No temporal indexing: SQLite doesn't have temporal indexes. For small datasets (thousands of memories), a sequential scan with WHERE clause is fast enough.
  • Asymmetric filtering: "since" and "before" can be combined for a time range. "asOf" is a shorthand for "before" with historical flag.

Trade-off: True bi-temporal querying requires tracking both valid time and transaction time for every fact, including supersession chains. Seme currently only tracks observed_at and recorded_at (set to the same value). A full bi-temporal implementation would track when facts were superseded and allow "what did we believe at time X?" queries, which is more complex but more powerful.
