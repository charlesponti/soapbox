Voice + background agents

One low-latency voice loop up front, with the slow work happening in the background. The user holds a single conversation; the system fans out, monitors, and reports back — never putting the voice on hold.

Product — how it feels

The promise is simple: talk, and things get done. The user never manages tasks, watches spinners, or asks “is it ready yet?” Every spoken turn gets an immediate spoken reply — under 500 ms — while slow work happens in the background.

Say “find me the cheapest flight to Lisbon next month and hold off on booking.” The voice answers right away — “On it, checking options now” — and a research agent spends the next 3 minutes on the slow work: searching, comparing, pricing. You keep talking about something else entirely. When the options are ready, the voice tells you, unprompted: “Got three options, the cheapest is Thursday at 6pm.”

  • Interruptible by default. Say “stop that” at any moment — mid-sentence, mid-task. The voice hears it on the same loop it always listens on, stops the task, and confirms what was stopped. No mode to enter, no button to find.
  • Proactive, not polling. Completions, failures, and cancellations arrive as announcements, not as answers you have to ask for. “How's that going?” works too — it's just a read of the same progress store.
  • Agents are invisible. There is exactly one personality, one voice, one thread of conversation. Background work never gets a name, a separate chat, or a notification channel.
  • Consequential actions get a read-back. Research is silent; spending money, sending messages, or deleting things always comes back as “here's what I'll do — go ahead?” before it happens.

Architecture

Technical — how it works

The system is two planes joined by exactly one coupling: a progress store. The foreground plane owns latency; the background plane owns tools and time. Neither calls into the other directly.

  • Voice loop (foreground). Streaming STT → turn detection → voice LLM → streaming TTS. Its context holds the conversation plus a table of live task ids — never tool output, never documents, never search results. Small context is what keeps replies under 500 ms.
  • Orchestrator. Classifies every turn into one of four moves: answer now (chit-chat, clarifications),spawn (new work), status check (“how's that going?”), or cancel (“stop that”). Spawns are fire-and-forget: spawn_task returns an id in milliseconds and the voice moves on.
  • Background agents. Each gets the full task brief, its own context window, and full tool access — search, code, files, bookings, long-polling APIs. They write heartbeats, partial results, and terminal states to the progress store, plus artifacts to an artifact store. They never speak and never see the conversation.
  • Progress store + event fan-in. The only shared state: task records (id, state, percent, latest checkpoint) and an append-only event log (started, update, done, failed, cancelled). The voice reads it on demand and receives terminal events, which it speaks at the next turn boundary.

Lifecycle of a task

  1. Turn arrives. Orchestrator classifies it as new work.
  2. spawn_task(type, args) returns a task id. It adds no extra model round-trip on top of the reply.
  3. Voice acknowledges in the same breath as answering: “On it — checking now.” The user perceives zero waiting.
  4. Agent executes with tools, writing heartbeats (state, percent, checkpoints) to the store. Partial results accumulate for free.
  5. “How's that going?” → voice reads the latest heartbeat and paraphrases it. No agent is ever woken for this.
  6. Done event → voice announces and presents the result, with the receipt (sources, price, confirmation number) attached.
  7. Failed ×3 → dead-letter to the store → voice explains plainly and offers the next move (“want me to try a different source?”). Failures are spoken, never silent.
  8. “Stop that” → cancel_task(id) → agent halts at the next checkpoint, store records cancelled, voice confirms what was stopped and what (if anything) survived.

The three hard problems

1. Latency isolation. The voice context must stay small forever. Agents summarize into the store; only summaries and terminal results ever flow back up. If background output leaks into the voice context, replies slow down and the whole illusion breaks — so the store schema is the budget, not a suggestion.

2. Cancellation. Cancel is cooperative: agents poll a cancel token at checkpoints and halt cleanly, leaving partial work resumable. The voice must always be able to say exactly what stopped and what survived — “stopped the search, kept the two quotes I already had.”

3. Staleness. Long tasks race changing intent. Every result carries the request it answers; if a newer turn supersedes it, the old task is cancelled rather than announced. No delivering yesterday's answer to today's question.

API sketch

spawn_task(type, args) -> task_id        // ms, never blocks
check_status(task_id) -> TaskRecord      // heartbeats, checkpoints
cancel_task(task_id) -> Ack              // cooperative, checkpointed

TaskRecord = { id, state, pct, summary, artifacts[] }
  state = queued | running | done | failed | cancelled
Event    = started | update | done | failed | cancelled
Retry    = 3 tries, exp backoff -> dead-letter -> voice speaks it
