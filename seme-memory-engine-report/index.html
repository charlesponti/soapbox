Technical report · Seme · November 2026

How Seme remembers, and what we changed after testing it

Seme is a memory system for AI assistants. We built a fake year of one person's life, fed it in, and checked whether Seme could still answer questions about it afterward.

Short version

Seme forgets things too fast. Turning off its automatic fading kept far more facts. A simple rule, keeping only the most recent memories, works surprisingly well. A smarter rule, which combines each topic's history into one dated note, did better still at the same size. We also found four bugs in how Seme answers questions about the past, and fixed them.

Words used in this report

Memory
A single fact Seme has stored about the user, such as "lives in Denver" or "has a sister named Mira". Seme stores each one as a short record with a date.
Ingestion
Feeding text into Seme. Seme reads the text and pulls out the facts worth remembering. We ingested a year's worth of simulated messages, one at a time, the same way a real user's messages would go in.
Decay
Seme's automatic fading. The longer since a memory was last confirmed, the less confident Seme is in it. Once it fades below a cutoff, Seme stops returning it when asked. Decay is on by default. "Decay off" means memories never fade, so anything Seme stored stays available.
Strategy
A rule for what to keep. Each strategy below is one rule applied to the same stored memories, so the rules can be compared fairly.
Budget
A cap on how many memories a strategy is allowed to keep. We count memories, not tokens, because a memory is what a user actually stores. Token counts are reported alongside.
Token
A chunk of text, roughly three-quarters of a word. Models are priced and limited by tokens, so the size of the context Seme hands the AI matters.
Context
The memories Seme pulls out to answer one question. The AI reads only these when it answers.
Accuracy
The share of test questions answered correctly, as a percentage. We ask 108 questions per strategy.
Point
One percentage point of accuracy. "Decay costs 9 points" means the score is 9 percentage points lower with decay on.
Noise
Random variation. Running the same test twice does not give the same score. In our runs, the same strategy moved between 5 and 8 points with nothing changed. A gap smaller than that could be luck, so we ignore it.
As-of question
A question about a past date, such as "Which city did I live in on January 28?" Seme has to remember what was true on that day, not what is true now.
Superseded
Replaced. When a fact changes, such as moving from Austin to Denver, Seme marks the old fact as superseded, meaning it used to be true and is not anymore.

What we tested

We wrote a generator for a fictional person's year. It produces about 127 messages spread over twelve months. Some facts change along the way: the person moves, changes jobs, or changes diet. Some messages correct an earlier mistake. Some mention one-off events, like an injury. Some include things that are not facts, like a hypothetical or a quote, and should not be remembered as true. Then we ask 108 questions at four points in the year, such as "What city do I live in now?" and "Which city did I live in last March?"

Every run uses the same generated year, so strategies are compared on the same stored memories. We fed the messages through Seme with a real AI model, saved the state at each checkpoint, and then tested each strategy on a copy of that saved state.

The strategies

Keep everything, with decay (Seme as it ships)
Seme's default. Memories fade over time, and faded ones drop out.
Keep everything, decay off
The same memories, but nothing fades. This tells us how much fading costs.
Keep the most recent N (recency)
No fading. Keep only the N memories that were recorded most recently, and drop the rest. This is the simplest possible budget rule, so it's the baseline any smarter rule has to beat.
Merge history, then keep N (consolidation)
When a fact changed over time, combine its whole history into one note. For example, instead of three separate records (Austin, Boston, Denver), keep one: "history: Austin until February 2026; Boston until 2026-05-01; now Denver since 2026-05-01". Then apply the same budget of N memories. The idea is that one merged note answers both "where do I live now" and "where did I live in March".

How much to trust these numbers

We ran the whole thing twice from scratch. The second run used the bug fix described below and different dates for the simulated year. Scores moved 5 to 8 points between the two runs, even for strategies we didn't change. That's noise. So we only trust a difference when it shows up in both runs. Two differences survive that test: merging history beats keeping the most recent memories at budgets of 10, 20 and 30, and turning decay off helps in both runs. Questions about past dates are a small group, about nine per run, so one question changes their score by about 11 points. Treat those numbers as hints, not measurements.

What we learned

Forgetting costs more than it looks

Turning decay off raised the overall score by 9 points in the second run and 17 in the first. The biggest loss is one-off events. One example: the simulated person says they tore their ACL while skiing. Seme stores that as a fact but gives it a fast fade. Within about nine months it fades below the cutoff, and Seme stops returning it. The memory is still there, Seme just never brings it up. So with decay on, the system quietly drops anything important that happened once. It does this without any budget, and without checking how important the memory was.

Keeping only the most recent memories is a surprisingly good baseline

Keeping the 30 most recent memories, about 60% of what Seme stored, gets 74% in the second run and 82% in the first. Keeping everything with decay off gets 91% and 92%. Any smarter rule has to beat this simple one at the same size, not just beat keeping everything. The simple rule fails in a predictable place: it throws away old facts first, and those are the ones needed to answer "what was true back then" or "what did I used to say".

Merging history beats keeping recent memories, at a cost

The merge strategy keeps one note per topic, with the dated history inside it. Averaged over both runs, it beats keeping the most recent memories by about 6 points at a budget of 10 (59% vs 53%), 4 points at 20 (78% vs 74%), and 11 points at 30 (89% vs 78%). At 45 the two are within noise. Most of the gain is on past-date questions and one-off events.

It has two costs. First, questions about when someone first said something got worse in one run and better in the other, so we can't call that a clear loss. Second, the merged notes are long. At a budget of 30, the AI gets about 279 tokens of context per question, versus 163 for keeping recent memories. That's about 70% more text for the same number of memories. A cheaper version of the merge, where a model writes a short summary, is the next thing to test.

Four bugs in how Seme answers questions about the past

Questions about past dates scored between 0% and 67%. We traced it to four separate problems:

  1. Seme only looked at current facts. When asked about a past date, it ignored any fact that had since been replaced, even though that fact was true on the date being asked about. Fixed: it now considers every fact that was true on that date.
  2. Seme checked fading against today. A fact's confidence should be judged as of the date being asked about, not today. Fixed.
  3. A date was passed under the wrong name. The service passed the date in one field, and the search code read it from a different field. Our first attempt at fixing bug 1 read the wrong field, found no facts at all, and dropped the past-date score to 0%. A debug run on a saved copy of the data found it.
  4. Replaced facts lost their search index. When a fact was replaced, Seme deleted the index entry that lets it be found by meaning, not just by exact words. So old facts could only be found by exact words. Fixed: the index entry is kept. In the second run, keeping everything with decay on went from 33% to 67% on past-date questions.

One caution: memories stored before the fix don't have that index entry. They can still be found by exact words, but not by meaning, until the store is rebuilt from the original messages.

Limits of this test

  • Three simulated people, run twice. That's a small sample, and the past-date group has only about nine questions.
  • The messages are generated, so they're tidier than real conversation. Real messages would be harder to read.
  • The grader is strict word matching. It can give credit to an answer that hedges between two answers, so we read the stored memories behind every wrong answer before trusting a score.
  • Merged notes are written by a fixed rule, not by a model, so they are not yet as readable as they could be.

What's next

  1. Have a model write the merged notes instead of the fixed rule, and measure the length and accuracy.
  2. Add more simulated people, and hold some back, so a new rule isn't tuned on the same people that grade it.
  3. Recompute the search index for merged notes, so they can be found by meaning too.
  4. Run the same test on an outside benchmark, to check the results aren't specific to our generated year.
