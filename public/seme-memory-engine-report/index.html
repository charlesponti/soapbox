Seme Memory Engine Report

What we built, how we measured it, and what the measurements changed about our design.

Abstract

Seme is a local-first memory engine for AI companions, backed by SQLite with keyword, vector and graph retrieval. We built a longitudinal benchmark that generates a synthetic year of one person's life, ingests it through the real extraction path with real models, and asks questions at four checkpoints. On three seeds (108 questions per strategy) we found that Seme's default time decay costs about 17 points against keeping the same memories, that a plain recency budget is a strong baseline, and that merging each fact's history into one dated memory beats recency at every budget we tried. Along the way we found four retrieval bugs in the as-of path. Two are fixed and verified on the benchmark; one fix needs a re-ingest before we can measure it.

1. The system

Seme stores memories as rows with a subject, predicate and value, plus provenance, observation time, a decay class and a confidence. Writes go through an extraction pipeline that proposes candidate memories from each episode, a resolver that decides whether a candidate is new, a reinforcement of an existing memory, or a supersession of one, and a retrieval engine that fuses three ranked signals (content-word match, sqlite-vec similarity, and entity-graph neighborhood) with reciprocal-rank fusion. Retrieval drops memories whose effective confidence falls under a floor, where effective confidence is confidence times an exponential decay on the time since last reinforcement.

Extraction runs on Claude Haiku 5.5 through OpenRouter. Embeddings are qwen3-embedding:4b at 1024 dimensions, served by Ollama. Answers come from a separate model given only the retrieved memories.

2. Achievements

  • Longitudinal benchmark. A seeded generator builds a life of about 127 episodes over twelve months: drifting facts (city, employer, diet), corrections, habits, one-off events, hypotheticals and quotes that must not be stored as facts, distractors, and questions that have no answer in memory. The fingerprint of each generated life is hashed so that runs are comparable.
  • Snapshot-based evaluation. Ingestion with real models is the slow, paid step, so we run it once per seed and snapshot the store at each checkpoint. Every strategy then runs on fresh copies of the same snapshots, so strategies are compared on identical memories.
  • Four as-of fixes. Historical queries searched only current memories; decay was measured against today instead of the query date; the service passed the as-of date under a different name than the retrieval engine read; and superseding a memory deleted its vector, so old values were reachable only by keyword. Details in section 5.
  • A consolidation strategy that merges a slot's history into one dated memory and then enforces a budget. It is deterministic and uses no model call.

The installable-app work (single process, CLI, first-run setup) is in progress on a branch and is not finished or verified end to end. This report covers the memory-engine research only.

3. Method

Each question is graded by exact match against accepted phrases, with forbidden phrases checked only in sentences that are not framed as past. Abstention questions count as correct only when the answer says the store does not know. The grader has a known soft spot: an answer that hedges between two values can pass if the right one is stated last. We read the memory dump for every failure before trusting a number.

The life ends on the day of the run, so wall-clock decay sees realistic memory ages. Budgets are measured in memory count, since that is what a user pays for. Token cost is reported alongside it.

How much to trust these numbers

Overall figures move four to five points between identical runs. The as-of and one-off groups have about nine questions each across the three seeds, so one question shifts as-of by eleven points. Recency at 45 beats keep-all with decay off, but it keeps 45 of about 48 memories, so that gap is noise rather than a finding.

5. Findings

Decay is an unbudgeted forgetting policy

Turning decay off on the same memories moves overall accuracy from 74 to 92. The loss is concentrated in one-off facts. One example: "I tore my ACL while skiing" is stored as a fact with importance 0.4 and a fast decay class. After roughly nine months its effective confidence falls under the retrieval floor, and the memory stays active the whole time. Retrieval never returns it. Decay is therefore doing budget-like forgetting, but it ignores importance and never shows up as a budget.

Recency is a strong baseline

Keeping the thirty most recent memories, about 60% of the store, scores 82%. Keeping everything with decay off scores 92%. Any new policy has to beat the recency curve at equal memory count, not keep-all. The curve breaks in the same place every time: corrected facts and past states, which are exactly the memories recency discards first.

Merging a slot's history beats recency

The consolidation strategy keeps one memory per subject and predicate, with its dated history in the text, for example history: Austin (until 2026-02-01); current: Denver (since 2026-02-01). It beats recency at every budget by 3 to 6 points overall (59 vs 54 at budget 10, 78 vs 75 at 20, 89 vs 82 at 30). The gain is mostly on as-of questions (44 vs 11 at budget 30) and one-off facts. The cost is on provenance questions, such as "when did I first tell you this": 67 against 83 at budget 30, and 58 against 100 at budget 45. Merging makes a dated statement harder to recover. Using a model to write the merged abstraction is the next thing to test.

As-of retrieval had four bugs

As-of questions scored between 33% and 56% for a while, and reading why turned up four separate problems:

  1. Wrong candidate pool. Historical queries searched only active memories. A value that was true on the query date and has since been superseded never entered the candidates. Fixed: the pool is every memory observed by the query date and still valid then.
  2. Wrong clock. Decay was measured at wall-clock now, not at the query date. Fixed.
  3. Wrong date source. The service passes the as-of date as to, while the retrieval engine read only asOf. Our first fix to (1) read only asOf and fell back to today, which emptied the pool and dropped as-of accuracy to 0%. A debug run on a snapshot found it, and the sweep was rerun. This one is worth remembering: an empty result can look like a retrieval miss when it's really a plumbing error.
  4. Superseded memories lost their vectors. Superseding deleted the incumbent's vector row, so semantic search could not reach an old value at all. Fixed in the resolver: vectors are kept for superseded rows, and historical vector search widens its window before filtering to the pool. Not yet measured, because our snapshots predate the change. Until stores are re-ingested, old superseded rows have no vectors.

6. Limitations

  • Three seeds and 108 questions. Small groups such as as-of and one-off are directional only.
  • The life is synthetic. Templated phrasing makes extraction easier than real conversation will be.
  • Consolidation is deterministic. We have not tested a model-written abstraction, and a model might recover provenance that merging loses.
  • The grader is exact match. It can credit hedged answers and must be read against the memory dump.
  • Embeddings for merged memories are not recomputed in the sweep, so vector search still sees the pre-merge text.

7. What's next

  1. Re-ingest the three seeds so the vector fix for superseded memories is measured.
  2. Test a model-written abstraction in place of the deterministic merge, and check provenance recovery.
  3. Add seeds and a dev/test split so the next policy is not tuned on the seeds that report it.
  4. Run the same harness on LongMemEval for an external check.
